Multi-Tenant SaaS: One Codebase, Seven Customers

March 2026

How do you serve seven enterprise customers—each with different auth providers, different business rules, different UI theming, and different data sources—from a single deployment? Not seven forks. Not seven branches. One codebase, one CI/CD pipeline, one deployment artifact. That was the constraint we set when the platform had three customers and it became obvious we would not survive the next two years maintaining per-client branches. What followed was a ground-up rearchitecture into a config-driven multi-tenant system that cut onboarding time from six-plus weeks to under five days and directly enabled three new enterprise contracts.

Why Database-Per-Tenant

The first architectural decision was isolation model. There are three common strategies for multi-tenant data isolation: shared schema (all tenants in one database, distinguished by a tenant ID column), schema-per-tenant (one schema per customer inside a shared database), and database-per-tenant (completely separate databases). We chose database-per-tenant, and the reasons were non-negotiable.

Two of our enterprise customers operate in regulated industries where compliance audits require demonstrable data isolation. Shared-schema architectures fail this bar—an auditor will not accept a WHERE tenant_id = ? clause as proof that Customer A's data is isolated from Customer B's. One customer had it written into their contract: their data must reside in a physically separate datastore. Schema-per-tenant gets closer, but backup, restore, and migration operations still affect the shared database engine, which creates risk surface area during audits.

Database-per-tenant gives us complete isolation. Each customer's data lives in its own MongoDB replica set. Backups are independent. Migrations can be rolled out per-tenant, which is critical when one customer is on a slower approval cycle. The trade-off is operational: we now manage six replica sets (with a seventh provisioned). But the compliance clarity is worth it.

Tenant Resolution

Every inbound request must resolve to a tenant context before anything else happens. We handle this through an encrypted customer identifier embedded in the JWT. When a user authenticates—whether through SAML, OAuth2, or a custom SSO flow—the auth layer issues a token containing an encrypted tenant ID. The API gateway middleware decrypts this, resolves it against the tenant registry, and attaches the full tenant context (database connection, config profile, feature flags) to the request object.

For inter-service communication, the pattern extends. Services do not re-authenticate on every hop. Instead, they propagate an encrypted context header that carries the tenant ID, the originating service identifier, and a timestamp. The receiving service validates the encryption, checks the timestamp against a 30-second window to prevent replay attacks, and resolves the tenant context from there.

Here is the core middleware pattern:

// Tenant resolution middleware
async function resolveTenant(req, res, next) {
  const token = req.headers.authorization?.split('Bearer ')[1];
  const serviceContext = req.headers['x-tenant-context'];

  let tenantId;

  if (token) {
    // External request: decrypt tenant ID from JWT
    const decoded = await verifyAndDecrypt(token, TOKEN_SECRET);
    tenantId = decoded.tenantId;
  } else if (serviceContext) {
    // Inter-service request: validate encrypted context header
    const ctx = decrypt(serviceContext, SERVICE_SECRET);
    const age = Date.now() - ctx.timestamp;
    if (age > 30_000) {
      return res.status(401).json({ error: 'Context expired' });
    }
    tenantId = ctx.tenantId;
  } else {
    return res.status(401).json({ error: 'No tenant context' });
  }

  // Resolve tenant config and DB connection
  const tenant = await tenantRegistry.resolve(tenantId);
  if (!tenant) {
    return res.status(403).json({ error: 'Unknown tenant' });
  }

  req.tenant = tenant;         // full config object
  req.db = tenant.dbConnection; // pre-pooled connection
  next();
}

This middleware sits at the top of every service's request chain. By the time a route handler executes, req.tenant contains the full configuration profile—auth provider settings, feature flags, UI configuration, notification preferences—and req.db points to the correct database. No downstream code ever needs to think about which tenant it is serving.

Config-Driven Everything

The real leverage in this architecture is not the isolation model. It is the config layer. Every dimension of customer variation is expressed as configuration, not code. This includes:

  • Auth providers: SAML for three customers, OAuth2 for two, custom OIDC for two. The auth module reads provider type, endpoints, certificate paths, and claim mappings from config.
  • Business rules: Approval workflows, validation logic, notification triggers, rate limits. Each customer has a rules profile that the engine evaluates at runtime.
  • UI layouts and navigation: Which modules appear in the sidebar, which dashboard widgets load, which features are visible. All driven by a layout config per tenant.
  • Theming: Over 60 color tokens, logo URLs, font preferences, favicon. The frontend pulls the theme config at login and applies it before the first render.
  • Notification preferences: Email templates, webhook endpoints, Slack integrations, digest frequency. Fully per-tenant.
  • Data source routing: Some tenants connect to external APIs for enrichment data. The connector configs—endpoints, auth credentials, polling intervals—are all stored per-tenant.

All of this lives in a dedicated configuration database. When a tenant context is resolved, the config is loaded (and cached with a short TTL). Changing a customer's auth provider from OAuth2 to SAML is a config update, not a code change. Adding a new dashboard widget for one customer does not affect the other six.

The Onboarding Win

Before this architecture, onboarding a new enterprise customer meant forking code, customizing auth integration, building their business rules into the application, styling their UI, and deploying a separate instance. Minimum timeline: six weeks, often longer. It required dedicated engineering effort and introduced a maintenance branch that would drift from the main codebase.

After the rearchitecture, onboarding is a configuration exercise. Provision a new MongoDB replica set. Create the tenant entry in the registry. Define the config profile: auth provider details, business rules, UI layout, theme tokens, notification settings, data source connections. Run the seed scripts. Total time: under five days, and most of that is waiting on the customer to provide their IdP metadata and approve the theme mockup.

This directly enabled signing three new contracts. Sales could commit to onboarding timelines that were previously impossible. The architecture became a competitive advantage.

Network Isolation and Security

Multi-tenancy at the application layer is not enough if the network layer is flat. We run VPC-per-product isolation, meaning each major product vertical operates in its own virtual private cloud. Services within a VPC communicate over private subnets. Cross-VPC traffic routes through encrypted tunnels with mutual TLS.

Inter-service authentication uses short-lived encrypted tokens scoped to specific service pairs. A service cannot call another service it is not explicitly authorized to reach. The encrypted context headers described earlier are part of this—they prevent a compromised service from fabricating tenant contexts for tenants it does not serve.

The Trade-offs

This architecture is not free. Managing six MongoDB replica sets (soon seven) requires operational investment. Monitoring, alerting, backup verification, capacity planning—all multiplied by the tenant count. We built tooling to automate most of this, but the complexity is real.

Config complexity is its own form of tech debt. When everything is configurable, the configuration space becomes large. We have seen cases where a subtle interaction between a business rule config and a notification config produced unexpected behavior for one tenant. Testing across all tenant configurations is essential but expensive. We run a nightly suite that boots each tenant's config profile and validates critical paths.

Schema migrations require coordination. Even though each tenant has its own database, the application code expects a consistent schema. We run migrations sequentially, tenant by tenant, with automated rollback if any tenant fails. This is slower than a single migration but significantly safer.

Debugging across tenants

When a bug appears, the first question is always: is this tenant-specific or global? We added tenant ID to every log line and every trace span. Filtering by tenant in our observability stack lets us answer that question in seconds rather than minutes.

Lessons

Config-driven architecture is the most underrated scaling decision you can make. It is not glamorous. It does not make for exciting conference talks. But it is the difference between a platform that can onboard a new enterprise customer in days versus one that requires weeks of custom engineering.

The key insight is that most customer variation is not algorithmic—it is parametric. Customers do not need fundamentally different code. They need different values fed into the same code. Once you internalize that distinction, the architecture follows naturally: extract every axis of variation into configuration, build a robust resolution layer, and invest in tooling to manage the config lifecycle.

Seven customers, one codebase, zero per-client branches. The system is not perfect—config complexity is real, operational overhead is real—but the alternative was a branching strategy that would have collapsed under its own weight by customer number four. If you are building a B2B SaaS product and you are not yet thinking about config-driven multi-tenancy, start now. The migration only gets harder.
