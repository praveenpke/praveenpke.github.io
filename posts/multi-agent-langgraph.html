Building Multi-Agent Systems with LangGraph

March 2026

Single-chain LLM architectures hit a wall fast. You can prompt-engineer your way through a straightforward Q&A flow or a simple RAG pipeline, but the moment your task has interdependent subtasks that require different reasoning strategies, different tool access, and different model trade-offs, a monolithic chain starts to buckle. The context window bloats. The prompt becomes a tangled mess of conditional instructions. Error recovery is nonexistent because the whole chain is one undifferentiated blob of state.

Multi-agent systems solve this by decomposing a complex workflow into specialized agents, each with a focused prompt, its own tool set, and a well-defined contract for what it reads from and writes to shared state. The orchestration layer handles routing, parallelism, and checkpointing. The agents handle reasoning. LangGraph gives you the primitives to build this cleanly: a StateGraph where nodes are agents, edges are routing logic, and the state object is your single source of truth.

This post walks through how I built TripForge, a multi-agent travel planning system, to illustrate the patterns that matter most when you move from single-chain to multi-agent.

The Architecture: Five Agents on a StateGraph

TripForge plans multi-city trips. A user says something like "Plan a 10-day trip through Japan, budget $5,000, I want temples and street food." The system produces a day-by-day itinerary with routes, hotels, activities, and a reconciled budget. That workflow decomposes into five agents:

  • Route Planner — determines the city-to-city sequence, transit modes, and timing. This is the reasoning-heavy agent: it needs to consider geography, travel time, and how the route affects downstream hotel and activity options.
  • Accommodation Agent — finds and ranks hotels for each city segment, respecting the per-night budget allocation from the route plan.
  • Activity Agent — curates activities per city, matching the user's stated interests against availability and time constraints.
  • Budget Reconciler — aggregates costs from routes, accommodation, and activities, then determines whether the plan is within budget or needs adjustment.
  • Replanner — if the budget is blown, this agent identifies the highest-impact cuts and regenerates the relevant plan segments.

Here is the core graph definition:

from langgraph.graph import StateGraph, END
from langgraph.checkpoint.postgres import PostgresSaver

builder = StateGraph(TripState)

# Add agent nodes
builder.add_node("route_planner", route_planner_agent)
builder.add_node("accommodation", accommodation_agent)
builder.add_node("activity", activity_agent)
builder.add_node("budget_reconciler", budget_reconciler_agent)
builder.add_node("replanner", replanner_agent)

# Entry point
builder.set_entry_point("route_planner")

# After route approval, fan out to parallel agents
builder.add_edge("route_planner", "accommodation")
builder.add_edge("route_planner", "activity")

# Both converge at budget reconciliation
builder.add_edge("accommodation", "budget_reconciler")
builder.add_edge("activity", "budget_reconciler")

# Conditional routing from budget reconciler
builder.add_conditional_edges(
    "budget_reconciler",
    budget_decision,
    {
        "within_budget": END,
        "over_budget": "replanner",
        "needs_approval": END,  # human reviews
    },
)
builder.add_edge("replanner", "budget_reconciler")

# Human-in-the-loop gates
builder.interrupt_before(["route_planner", "budget_reconciler"])

checkpointer = PostgresSaver.from_conn_string(DATABASE_URL)
graph = builder.compile(checkpointer=checkpointer)

That is the entire orchestration topology in about 30 lines. Every behavioral concern — what the route planner actually does, how the budget reconciler reasons about trade-offs — lives inside the individual agent functions. The graph only defines flow.

Key Patterns

Parallel Fan-Out

Once the route is locked, accommodation and activity search are independent. There is no reason to run them sequentially. LangGraph supports this natively: when a single node has multiple outgoing edges, the targets execute in parallel. The graph runtime collects both results before advancing to the next node.

# The fan-out is implicit in the edge definition.
# Both edges originate from "route_planner":
builder.add_edge("route_planner", "accommodation")
builder.add_edge("route_planner", "activity")

# LangGraph runs accommodation and activity concurrently.
# budget_reconciler only fires once BOTH have written
# their results to TripState. The state reducer merges
# partial updates using the reducer functions defined
# on each field of TripState:

class TripState(TypedDict):
    route_plan: Annotated[RoutePlan, replace]
    accommodations: Annotated[list[Hotel], merge_lists]
    activities: Annotated[list[Activity], merge_lists]
    budget_status: Annotated[BudgetStatus, replace]
    messages: Annotated[list[BaseMessage], add_messages]

The Annotated reducers are critical. When two agents write to the same state concurrently, LangGraph needs to know how to merge. merge_lists concatenates; replace takes the latest write. Getting these wrong produces subtle, hard-to-debug state corruption.

Conditional Routing

The budget reconciler is the decision point. It examines total cost against the user's budget and returns one of three verdicts. The budget_decision function inspects the reconciler's output and returns a string key that maps to the next node:

  • within_budget — the plan is good. Proceed to the terminal node. The user gets their itinerary.
  • over_budget — route to the replanner, which trims costs and cycles back to the reconciler for another pass.
  • needs_approval — the plan is slightly over budget (within a configurable threshold). Pause for human review rather than automatically cutting.

This loop — reconciler to replanner and back — can execute multiple times. In practice, I cap it at three iterations to prevent runaway cycles. The replanner's state includes an iteration_count field, and on the third pass, it forces a "needs_approval" verdict regardless of budget status.

Human-in-the-Loop

LangGraph's interrupt_before is deceptively simple but architecturally significant. When the graph reaches a node listed in interrupt_before, it serializes the current state to the checkpointer and halts. The calling application receives a signal that the graph is paused. The user can review the proposed route, approve or modify it, and then resume the graph from exactly where it stopped.

This is not just a UX nicety. For TripForge, route approval is a correctness gate. The route determines everything downstream. If the user wants to swap Osaka for Hiroshima, you need that correction before the accommodation and activity agents burn tokens on the wrong cities. The second gate, at budget reconciliation, lets users accept a slightly-over-budget plan rather than forcing automated cuts they might not want.

State Checkpointing

The PostgresSaver checkpointer persists the full graph state after every node execution. This buys you three things: resumability (users can close the browser and come back), debuggability (you can replay any step from a checkpoint), and fault tolerance (if the activity agent fails mid-execution, you restart from the last successful checkpoint, not from scratch). In a production deployment, this is non-negotiable. LLM calls are expensive and slow. Losing a partially completed plan because of a transient API error is unacceptable.

Per-Agent Model Selection with LiteLLM

Not every agent needs the same model. The route planner is doing genuine multi-constraint reasoning — balancing geography, transit logistics, time allocation, and user preferences. That agent gets Claude Sonnet. The accommodation and activity agents are mostly doing structured retrieval and ranking, which is well within the capability of a faster, cheaper model. Those run on Claude Haiku.

LiteLLM makes this trivial. Each agent function instantiates its own ChatLiteLLM client with the appropriate model string. The orchestration layer does not care — it just calls the agent function and collects the state update. This pattern cut our per-plan inference cost by roughly 40% compared to running Sonnet everywhere, with no measurable quality degradation on the structured-output agents.

When Multi-Agent Is (and Isn't) Worth It

The orchestration complexity is real. You are now debugging a distributed system, not a linear chain. State reducers can silently corrupt data. Conditional routing logic can create infinite loops if you are not careful with termination conditions. Checkpoint storage adds infrastructure cost. The fan-out pattern means you are paying for concurrent LLM calls that might partially fail, requiring retry logic at the graph level.

Multi-agent is worth it when:

  • Your task naturally decomposes into subtasks with different tool and model requirements.
  • Subtasks can run in parallel, and the wall-clock time savings matter.
  • You need human checkpoints at specific decision points, not just at the end.
  • The workflow has conditional branches — different paths based on intermediate results.
  • You need fault tolerance and resumability for long-running plans.

Stick with a single chain when:

  • The task is fundamentally sequential with no meaningful branching.
  • All subtasks need the same tools and the same model.
  • The total token budget is small enough that a single context window handles it.
  • You do not need intermediate human review.

LangGraph's contribution is not inventing multi-agent orchestration — these patterns existed long before it. Its contribution is giving you a declarative, inspectable graph that separates orchestration topology from agent logic, with first-class support for checkpointing and human-in-the-loop. For a system like TripForge, where the workflow is complex but well-structured, that abstraction pays for itself quickly. The key lesson: design your state schema and reducers as carefully as you design your prompts. The graph is only as reliable as its state management.
