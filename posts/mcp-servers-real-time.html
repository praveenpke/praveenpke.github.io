MCP Servers: Extending LLMs with Real-Time Computation

March 2026

Ask Claude where Saturn is in the sky tonight and you will get an answer. It will be articulate, confident, and wrong. Not because the model is broken, but because planetary positions change by the hour and the training data is a frozen snapshot of the past. The model has no choice but to hallucinate a plausible longitude from patterns it memorized months or years ago. This is the fundamental limitation: LLMs are extraordinary at reasoning over language, but they cannot compute. They interpolate. When the task demands a precise, real-time numerical result, interpolation is not enough.

This gap between what an LLM knows and what it can calculate is not a flaw to be patched with more training data. It is a category difference. And it turns out there is an elegant way to bridge it.

The Model Context Protocol

In late 2024, Anthropic released the Model Context Protocol (MCP) as an open standard for connecting LLMs to external tools, data sources, and services. The analogy that stuck: MCP is like USB-C for AI. Before USB-C, every device had its own proprietary connector. Before MCP, every tool integration was a bespoke piece of glue code wired into a specific application. MCP defines a universal transport layer so that any compliant server can expose capabilities to any compliant client.

The protocol is simple by design. An MCP server declares a set of tools with typed input schemas. A client (like Claude Desktop) discovers those tools, presents them to the language model, and the model decides when to call them based on the user's request. The server runs the computation and returns structured results. The model then interprets those results in natural language. This separation is critical: the server is deterministic, the model is expressive, and neither tries to do the other's job.

MCP supports multiple transports, but the simplest is stdio — the server runs as a subprocess, communicating over standard input and output via JSON-RPC. No HTTP, no ports, no authentication headaches. For local tools that need to do heavy computation, stdio is ideal.

AstroMCP: A Case Study

To test what MCP could do for real-time computation, I built AstroMCP: a server that gives Claude access to the Swiss Ephemeris, the same astronomical engine used by research institutions worldwide. It is backed by NASA's JPL DE441 ephemeris files, which encode planetary positions with sub-arcsecond precision across a 15,000-year span. The server exposes 12 tools over stdio transport, covering planetary positions, house systems, aspect calculations, and transit lookups.

The architecture is straightforward:

Claude Desktop → MCP Server (Python, stdio) → Swiss Ephemeris (NASA JPL DE441)

The user asks a question in natural language. Claude recognizes it needs positional data and calls the appropriate tool. The server computes the answer using the ephemeris and returns raw numerical data. Claude then weaves that data into a coherent response. At no point does Claude attempt to calculate a planetary longitude on its own.

I built the server using Anthropic's FastMCP SDK, which strips away the protocol boilerplate and lets you define tools as decorated Python functions with Pydantic models for input validation. Here is what a tool definition looks like in practice:

from fastmcp import FastMCP
from pydantic import BaseModel, Field

mcp = FastMCP("AstroMCP")

class PlanetPositionRequest(BaseModel):
    planet: str = Field(
        description="Planet name (Sun, Moon, Mars, etc.)"
    )
    year: int = Field(description="Year")
    month: int = Field(ge=1, le=12, description="Month")
    day: int = Field(ge=1, le=31, description="Day")
    hour: float = Field(
        default=12.0,
        description="Hour in UTC (decimal, 0-24)"
    )
    zodiac: str = Field(
        default="tropical",
        description="Coordinate system: tropical or sidereal"
    )

@mcp.tool()
def get_planet_position(req: PlanetPositionRequest) -> dict:
    """Get the ecliptic longitude of a planet
    at a specific date and time."""
    jd = compute_julian_day(
        req.year, req.month, req.day, req.hour
    )
    flags = SIDEREAL_FLAG if req.zodiac == "sidereal" else 0
    lon, lat, dist = calc_planet(req.planet, jd, flags)
    sign, degrees, minutes = lon_to_sign(lon)
    return {
        "planet": req.planet,
        "longitude": round(lon, 4),
        "sign": sign,
        "degrees": degrees,
        "minutes": minutes,
        "zodiac_system": req.zodiac
    }

The Pydantic schema does double duty. At runtime, it validates every input before the computation runs. At discovery time, MCP serializes the schema as JSON and sends it to Claude, so the model knows exactly what parameters each tool expects and what constraints they carry. The Field descriptions become part of the model's understanding of the tool.

Key Design Decisions

Separation of Concerns

The server is pure computation. It returns numbers, not narratives. Claude handles all interpretation, explanation, and conversational context. This means the server never needs to know what the user actually asked, and Claude never needs to perform arithmetic. Each component operates in its zone of competence.

Dual Coordinate Systems

Astronomy uses tropical coordinates (aligned to the vernal equinox), while Vedic and sidereal traditions use a different reference frame offset by roughly 24 degrees. Rather than building two servers, AstroMCP computes both from the same Swiss Ephemeris engine by toggling an ayanamsa correction. One tool, one codebase, two coordinate systems. The zodiac parameter lets Claude select the right one based on the user's context.

System Prompt Engineering

Giving Claude access to tools is not enough. Without explicit instructions, the model will sometimes blend tool-provided data with its own training knowledge, producing hybrid answers that are subtly wrong. The fix is a system prompt that constrains behavior: always call the tool for positional data, never estimate from memory, and clearly state when data comes from the ephemeris. This prompt engineering is as important as the server code itself. It turns tool access into tool reliance.

Results

The difference is not subtle. Without the MCP server, Claude's planetary position estimates are typically off by 10 to 30 degrees — the model might place Jupiter in Aries when it is actually in Taurus. With AstroMCP, positions are accurate to within 0.1 degrees of published ephemeris tables. That is the difference between a guess and a reference-grade calculation.

More importantly, the interaction feels the same to the user. They still ask questions in natural language. Claude still responds conversationally. The computation happens silently in the background. The only visible difference is that the answers are correct.

When to Build an MCP Server

Not every problem needs one. MCP servers make sense when the LLM needs something it structurally cannot provide on its own:

  • Deterministic computation — mathematical calculations, simulations, or algorithmic processing where approximate answers are not acceptable.
  • Real-time data — stock prices, weather, sensor readings, or anything that changes faster than a model can be retrained.
  • Domain-specific engines — physics simulators, financial models, medical dosage calculators, or any system where the logic has been validated by domain experts over decades.
  • Authoritative lookups — querying a database, a regulatory API, or a canonical data source where the model should not guess.

The pattern is the same every time: let the model handle language, let the server handle truth. MCP simply makes that handoff clean, discoverable, and standardized.

The hallucination problem is not going away. Models will always have a training cutoff, and they will always be tempted to fill gaps with plausible fiction. But with MCP, we can selectively replace fiction with computation — routing specific questions to systems that can answer them with certainty. The model becomes an orchestrator rather than an oracle. And honestly, that is a much more useful thing to be.
