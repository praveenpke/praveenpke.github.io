Real-Time Computation Engines at Scale

March 2026

Imagine you need to compute over 100 fields per entity, every 2 minutes, across more than 10,000 active entities. Now add the constraint that a single input change in one module can cascade through 5 other interdependent modules, each of which must recompute its outputs before the next one can proceed. And if any of those calculations are wrong, the consequences are not a degraded dashboard or a stale cache -- they are legal violations and safety incidents. This is the engineering reality of building real-time computation engines for high-stakes regulatory compliance.

The Problem Domain

Certain industries operate under strict regulatory frameworks where entities -- whether they are people, vehicles, assets, or operational units -- must continuously satisfy a set of quantitative rules. These rules often involve rolling time-window calculations: how much of X has this entity accumulated over the last 168 hours? Over the last 672 hours? Over the last 365 days? And critically, these thresholds are not just historical lookbacks. The system must also project forward: given the current schedule, will any entity breach a limit within the next 7 days?

Getting these numbers wrong is not an engineering inconvenience. It is a compliance failure with real-world repercussions -- fines, grounded operations, or worse. The system cannot afford eventual consistency. It needs to be correct, and it needs to be correct now.

Engine Architecture: Six Modules, One Dependency Graph

The computation engine is structured as 6 distinct modules, each responsible for a category of calculations. The modules are not independent -- they form a directed acyclic graph of dependencies.

Module A: Raw input aggregation (time-window rollups)
Module B: Derived limits (depends on A)
Module C: Threshold evaluation (depends on A + B)
Module D: Exception handling (depends on C)
Module E: Forward projection (depends on A + B + D)
Module F: Compliance status (depends on all above)

When a new input arrives -- say, a schedule change or a recorded activity event -- the engine determines which module is affected and triggers a targeted recomputation through the dependency chain. Module F always runs last, producing the final compliance verdict for the entity. This architecture means the engine is not a flat batch job. It is a reactive pipeline where the depth of recomputation depends on where the change enters the graph.

Why Not Microservices?

The tight coupling between modules is intentional. These calculations share intermediate state, and the cost of serializing and deserializing that state across service boundaries would destroy latency. The engine runs as a single deployable unit with clear internal module boundaries -- a modular monolith optimized for computational throughput rather than independent deployability.

Cascading Dependency Resolution

The naive approach to handling a change is simple: recompute everything. With 100+ fields across 6 modules, this is wasteful. The engine instead maintains a dependency map at the field level. Each computed field declares which inputs and upstream fields it depends on. When an input changes, the engine walks this map to determine the minimal set of fields that need recomputation.

The goal is not to be fast by skipping work. It is to be fast by knowing exactly which work matters.

This is implemented as a topological sort over the dependency graph. Changed inputs are flagged, and only fields reachable from those inputs are marked dirty. The engine then recomputes dirty fields in dependency order. In practice, a typical input change touches 15-30% of the total field set, saving significant compute on every cycle.

Rolling Time-Window Calculations

Three distinct time windows drive most of the regulatory logic: 168-hour (7-day), 672-hour (28-day), and 365-day windows. These are not calendar-aligned -- they are true rolling windows measured from the current timestamp.

The challenge with rolling windows is that they invalidate passively. Even if no new input arrives, the passage of time itself changes the calculation as old events fall off the trailing edge of the window. The engine handles this with a scheduled tick -- every 2 minutes, it re-evaluates all active entities, even if no new inputs have arrived. This tick ensures that time-based expirations are caught promptly rather than only when the next input happens to trigger a recomputation.

For efficiency, the engine pre-indexes events by their expiration timestamp. Rather than scanning the full event history on each tick, it checks which events have recently fallen outside each window boundary and adjusts the running aggregates incrementally.

The Predictive Layer

Historical compliance is only half the problem. Operators need to know: if we proceed with the current plan, will we violate any rules in the next 7 days? The engine answers this by running the same computation pipeline against forward-projected schedules.

This is not a separate system or a simplified approximation. It is the same engine, the same modules, the same dependency graph -- but fed with scheduled future events instead of recorded past events. The predictive layer iterates day-by-day through the forward window, evaluating compliance status at each projected point. This guarantees that the predictive output is consistent with the historical calculation logic, eliminating the drift that inevitably occurs when prediction and evaluation are implemented separately.

Config-Driven Rule Overrides

Not every entity operates under the same rules. Different customers, jurisdictions, or operational contexts may apply different thresholds, different window sizes, or different exception criteria. The engine supports this through a configuration layer that parameterizes every rule.

{
  "rule_set": "standard_v2",
  "overrides": {
    "window_168h_max": 60,
    "window_672h_max": 190,
    "exception_credits": true,
    "forward_projection_days": 7
  }
}

Rule overrides are resolved at computation time by merging the base rule set with customer-specific overrides. This keeps the computation code path singular -- there are no if (customer === X) branches. The same engine code handles all customers, parameterized entirely by configuration. This design decision pays dividends in testability: every code path is exercised regardless of which customer configuration triggers it.

Performance Profile

At steady state, the engine processes approximately 5 million calculations per day. The P95 engine latency -- measured from input receipt to final compliance status output -- is under 800 milliseconds. The 2-minute tick cycle means that in the worst case, a newly recorded event is reflected in compliance status within 2 minutes and 800 milliseconds.

The performance budget is tight but not extreme. The real constraint is not raw speed but consistency under load. During peak periods -- shift changes, bulk schedule uploads, system-wide recalculations -- the engine must maintain the same latency guarantees. This is achieved through careful work partitioning: entities are sharded across computation workers, and each worker processes its assigned entities sequentially, avoiding contention on shared state.

Testing as a First-Class Concern

In most systems, 80% test coverage is considered thorough. In a computation engine where incorrect output has legal consequences, 95-100% coverage is the floor, not the ceiling. Every edge case -- window boundary crossings, overlapping events, exception stacking, timezone transitions, leap seconds -- has dedicated test cases.

The test suite is enforced via pre-commit hooks. No code merges without passing the full computation test battery. This is not a CI nicety -- it is a hard gate. The test suite includes:

  • Unit tests for every individual field calculation across all 6 modules
  • Integration tests that verify cascading recomputation produces correct end-to-end results
  • Regression tests built from real-world incidents where edge cases were discovered in production
  • Property-based tests that verify invariants like "forward projection must never be more permissive than historical evaluation"

The cost of this test suite is significant -- it adds minutes to every commit. The cost of not having it is measured in compliance incidents.

Lessons Learned

Optimize for Correctness First

In high-stakes computation, the temptation to optimize for speed is constant. But a fast wrong answer is worse than a slow right one. The engine's architecture prioritizes auditability and determinism over raw throughput. Every computation can be traced back to its inputs. Every intermediate value is logged. When a regulator asks "why did you compute this value?", the system can produce a complete derivation chain.

Exhaustive Testing Pays Compound Interest

The upfront investment in comprehensive test coverage has a compounding return. Every new feature or rule change can be implemented with confidence that it does not break existing calculations. Engineers who join the team can make changes on day one because the test suite catches mistakes that would otherwise require years of domain knowledge to spot.

Configuration Over Code Branching

The decision to make rules config-driven rather than code-branched was one of the highest-leverage architectural choices. It reduced the combinatorial explosion of customer-specific code paths and made the engine testable with a single, unified test suite rather than per-customer test matrices.

Building real-time computation engines for regulated domains is an exercise in disciplined engineering. The patterns are not novel -- dependency graphs, incremental computation, rolling aggregates, config-driven behavior. What makes the work hard is the margin for error: zero. When the system says an entity is compliant, it must be right. When it predicts a future violation, it must be trustworthy. The architecture, the testing strategy, and the operational discipline all serve that single constraint. Correctness is the feature.
